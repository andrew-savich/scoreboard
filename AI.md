## 2. Architectural Evolution & Key Decisions (ADR Log)

This section logs the foundational architectural decisions, domain model choices, and structural evolution of the scoreboard library, explicitly documenting why certain initial design proposals were rejected in favor of simpler, production-ready alternatives.

### Architectural Decision Records

* **ADR-01: Domain Model & Snapshot Immutability**
  * **Context:** Active matches undergo frequent score updates while being queried concurrently by readers.
  * **Design Choice:** Represented the core entity as an immutable record (`Match`). Updates create lightweight, new record snapshots rather than mutating shared state in-place.
  * **Rationale:** Eliminates side effects and internal mutation race conditions when exposing state snapshots to external consumers. Modern JVM Garbage Collectors handle short-lived record allocations efficiently.

* **ADR-02: Simplification of Match Identity (Rejection of `MatchId` Wrapper)**
  * **Context:** Initial design proposals suggested introducing a dedicated Value Object wrapper class `MatchId(UUID value)` for match identification.
  * **Design Choice:** Rejection of custom wrapper types in favor of direct `java.util.UUID` usage across public API methods.
  * **Rationale:** Introducing a wrapper around a single `UUID` violated KISS/YAGNI principles, adding unnecessary object allocation overhead and cognitive boilerplate without providing additional domain type-safety for this library's scope.

* **ADR-03: Concurrency Control Strategy (`ReentrantReadWriteLock` vs. `synchronized`)**
  * **Context:** Need to support O(1) lookups by ID for updates/deletions, alongside deterministic ordering for summary retrieval under concurrent access.
  * **Design Choice:** Replaced global `synchronized` methods with a `ReentrantReadWriteLock` guarding an in-memory `Map<UUID, Match>`.
  * **Rationale:** Coarse-grained `synchronized` methods create unnecessary thread contention by forcing readers (`summary()`) and writers (`updateScore()`, `startMatch()`) to block each other globally. `ReentrantReadWriteLock` allows multiple concurrent readers to acquire state snapshots simultaneously without blocking, while write locks ensure strict atomicity during state mutations.

* **ADR-04: Deterministic Ordering & Counter State (`AtomicLong` vs. Primitive Under Lock)**
  * **Context:** Summary requires ordering by total score descending, breaking ties by the most recently started match.
  * **Design Choice:** Utilized an internal monotonic sequence counter for start ordering. Used an `AtomicLong` (or primitive `long` guarded strictly within the Write Lock) rather than floating system timestamps (`Instant`).
  * **Rationale:** Prevents tie-breaking bugs when matches start within the same millisecond or during system clock drift. Sorting is performed on a detached list snapshot outside the critical section to avoid stalling writers ($O(N \log N)$ sorting offloaded from write boundaries).

* **ADR-05: Public API Contract & Interface Decoupling**
  * **Context:** Exposing internal storage logic directly violates the Dependency Inversion Principle and limits future extensibility.
  * **Design Choice:** Extracted a pure Java interface (`Scoreboard`) defining core capabilities (`startMatch`, `updateScore`, `finishMatch`, `summary`), leaving `InMemoryScoreboard` as an internal, thread-safe implementation.
  * **Rationale:** Keeps the client API minimal, clean, and extensible without leaking thread-synchronization or state-storage mechanics.

* **ADR-06: Overflow Prevention & Fail-Fast Validation**
  * **Context:** Need to prevent integer overflow vulnerabilities when calculating total scores (`homeScore + awayScore`) and ensure strong invariant guarantees on input data.
  * **Design Choice:** Implemented explicit long-casting/overflow checks during summary sorting alongside strict Fail-Fast validation at API boundaries (`NullPointerException`, `IllegalArgumentException`, `IllegalStateException`).
  * **Rationale:** Guarantees predictable behavior under extreme input bounds without corrupting internal state or throwing silent arithmetic errors.
